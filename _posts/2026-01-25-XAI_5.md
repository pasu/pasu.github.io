# 当 LLM 开始学习“怎么建模”：从 Geometry 到 Procedural Modeling

刚刚看到一个 **LLM + CityEngine + CGA** 的工作，觉得很有趣，简单的了解了一下。

一开始我的感觉其实很普通：

> AI 又开始生成 3D model 了。

毕竟现在从 text-to-3D、image-to-3D，到 AI 操作 Blender，已经不是什么特别新的概念。

但仔细看之后，我发现这里真正有意思的事情并不是：

> **让 AI 生成一个建筑。**

而是：

> **让 AI 理解一个建筑应该怎么被建出来。**

这两件事情看起来很接近，但背后的思路其实完全不同。

而理解这个区别，我觉得可以从一个非常简单的东西开始：

**乐高积木。**

---

# 1. 如果 Geometry 是乐高积木

假设现在给我一盒最基础的乐高积木。

在计算机图形里，它们可能就是：

```text
Point
Line
Polygon
Cube
Plane
Cylinder
...
```

这些都是最基础的 Geometry。

单独看，它们没有什么特别的。

但是如果再给我一本说明书：

```text
Step 1: 从一个 footprint 开始
Step 2: 向上 Extrude 30m
Step 3: 分成 8 层
Step 4: 每层生成 facade
Step 5: 重复 windows
Step 6: 添加 balconies
Step 7: 生成 gabled roof
```

那么通过这些最基础的“积木”，我们就可以搭出一个复杂的建筑。

换一本说明书，又可以搭出完全不同的建筑。

所以从这个角度理解 Procedural Modeling，就非常直观了：

> **Geometry 是积木，而 Procedural Rules 是说明书。**

而 CGA 做的事情，正是把这本“说明书”变成一种计算机可以执行的语言。

---

# 2. CGA 保存的不是建筑，而是“怎么建建筑”

CGA（Computer Generated Architecture）是 CityEngine 用于 procedural modeling 的规则语言。

它和传统建模最大的区别，是它并不只是描述最终的 geometry，而是描述：

> **一个 shape 应该经过什么过程，逐渐变成最终的 geometry。**

例如：

```text
Lot
 ↓
Extrude
 ↓
Split into floors
 ↓
Repeat floors
 ↓
Split facade
 ↓
Repeat windows
 ↓
Add balconies
 ↓
Create roof
```

同时，我们还可以定义参数：

```text
floors = 8
floorHeight = 3.2
windowWidth = 1.5
roofShape = "gabled"
```

于是同一套规则，只要修改参数，就可以生成很多不同的建筑。

CityEngine 官方的 CGA 工作流也是从 initial shapes 出发，为 shape 指定 rule file 和 start rule，再由规则生成模型；attributes 可以暴露出来，让同一套规则产生不同结果。

所以我觉得理解 CGA 最简单的一句话就是：

> **Geometry 描述“结果”，CGA 描述“过程”。**

或者继续用乐高的比喻：

> **Geometry 是积木，CGA 是说明书。**

而这个区别，恰恰给 LLM 留出了一个非常有意思的位置。

---

# 3. 如果 CGA 是说明书，那么 LLM 可以帮人写说明书

传统 Procedural Modeling 有一个很现实的问题：

**人必须学会 procedural language。**

假设我只是一个城市规划师、建筑师或者普通 GIS 用户。

我的需求可能非常简单：

> “在这个地块上生成一个 8 层住宅建筑，保留 footprint，每层增加 balcony，底层开放一些，使用双坡屋顶。”

对于人来说，这句话已经非常明确了。

但对于传统 modeling system，我们还需要把它翻译成参数、operators 和 rules。

例如：

```text
buildingType = residential
floors = 8
keepFootprint = true
balcony = true
openGroundFloor = true
roofShape = gabled
```

然后进一步转换成：

```text
Footprint
 ↓
Extrude
 ↓
Split into 8 floors
 ↓
Create facade
 ↓
Repeat balconies
 ↓
Open ground floor
 ↓
Create gabled roof
```

这恰好是 LLM 很擅长的事情。

LLM 不一定需要自己去计算几万个 vertices，也不需要自己成为 geometry engine。

它可以负责：

```text
Understand human intent
        ↓
Extract constraints
        ↓
Understand modeling semantics
        ↓
Select modeling operators
        ↓
Generate / modify procedural rules
```

于是整个交互方式就发生了变化。

过去：

```text
Human
 ↓
Learn Modeling Tool
 ↓
Learn Modeling Language
 ↓
Write Rules
 ↓
Geometry
```

现在可以变成：

```text
Human
 ↓
Natural Language
 ↓
LLM
 ↓
Modeling Intent
 ↓
Procedural Rules
 ↓
Geometry
```

这时候 LLM 真正降低的，不只是“建模成本”。

它降低的是：

> **Human Intent 和 Modeling Process 之间的 translation cost。**

---

# 4. Python：从“积木”进一步变成“积木工厂”

但是实际的建模系统当然不会只有 `Cube`、`Plane`、`Polygon` 这些 primitive。

我们可以进一步把常用的 geometry operations 和 modeling components 封装起来。

例如：

```text
Python
│
├── Geometry
│   ├── Extrude
│   ├── Split
│   ├── Offset
│   └── Transform
│
├── Architecture
│   ├── Floor
│   ├── Facade
│   ├── Window
│   ├── Balcony
│   └── Roof
│
└── GIS
    ├── Parcel
    ├── Building Footprint
    ├── Road
    ├── Terrain
    └── Spatial Query
```

这样 Python 就像一个不断扩充的：

> **积木工厂。**

它把复杂的底层 operations 封装成更高级、更稳定、更容易调用的 building blocks。

于是 LLM 不需要每次从 vertex 开始重新发明轮子。

它可以组合已经存在的模块。

这也是为什么我觉得 **Python + Procedural Modeling + LLM** 是一个非常自然的组合。

---

# 5. PyPRT：把 Python 和 CGA 的 Procedural Runtime 接起来

继续往下看，就会遇到 PyPRT。

这里几个名字很容易混：

```text
CGA
RPK
PRT
PyPRT
```

可以粗略理解为：

```text
CGA Rules + Assets
        ↓
       RPK
        ↓
      PyPRT
        ↓
       PRT
        ↓
     Geometry
```

其中：

**CGA** 描述 procedural modeling logic。

**RPK（Rule Package）** 打包 rules 和相关资源。

**PRT（Procedural Runtime）** 执行 procedural rules。

**PyPRT** 则让 Python 可以调用 PRT。

于是 Python 可以负责整个 orchestration：

```text
GIS Data
   +
User Input
   +
LLM
   ↓
Python
   ↓
PyPRT
   ↓
CGA / RPK
   ↓
PRT
   ↓
Geometry
```

这就开始有点意思了。

因为 Python 本身又可以连接：

```text
GeoPandas
Shapely
NumPy
GIS APIs
LLM APIs
Databases
Web APIs
...
```

于是 CGA 不再只是 CityEngine 里面的一套建模规则。

它可以成为更大计算 pipeline 中的一个 **procedural modeling engine**。

---

# 6. 但这里有一个很重要的问题：LLM 一定要直接生成 CGA 吗？

我觉得不一定。

最激进的方式当然是：

```text
Natural Language
 ↓
LLM
 ↓
CGA Code
 ↓
Geometry
```

但真正做系统的时候，更实际的方案可能首先是：

```text
Natural Language
 ↓
LLM
 ↓
Structured Parameters
 ↓
Validated CGA Rules
 ↓
Geometry
```

比如用户说：

> “12 层住宅，每层有 balcony，双坡屋顶。”

LLM 只需要输出：

```text
floors = 12
buildingType = residential
balcony = true
roofShape = gabled
```

然后这些 parameters 去驱动已经经过验证的 CGA rules。

这样：

```text
LLM
 ↓
What does the human want?

CGA
 ↓
How should it be modeled?

PRT
 ↓
Execute it.
```

这其实是一个非常漂亮的分工。

LLM 负责不确定的 **semantic interpretation**。

CGA 负责明确的 **modeling knowledge**。

PRT 负责 deterministic **execution**。

人类软件工程折腾了几十年终于学会模块化，现在最好不要因为有了 AI，又兴奋地把所有东西塞回一个模型里。

---

# 7. 那么它和 OSM、CityGML、glTF 有什么区别？

走到这里，我觉得一个更有意思的问题出现了：

**CGA 和我们传统的 GIS / 3D representations 到底有什么区别？**

因为我们已经有很多东西：

```text
OSM
CityGML
glTF
OBJ
FBX
3D Tiles
...
```

为什么还需要 procedural representation？

关键在于：

> **它们实际上在回答不同的问题。**

---

## glTF / OBJ / FBX：它长什么样？

对于 glTF、OBJ、FBX 这样的 geometry / asset formats，我们通常已经拥有一个 model。

里面保存的是：

```text
vertices
triangles
normals
materials
textures
animations
...
```

它们解决的问题主要是：

> **这个已经存在的 3D object，应该怎样保存、交换和渲染？**

所以可以把它概括成：

```text
What does it look like?
```

它更接近最终结果。

---

# 8. CityGML：它是什么？

CityGML 又是另一个层次。

严格来说，CityGML 不能简单理解成一个 geometry format。

OGC 对 CityGML 3.0 的定义是用于虚拟 3D 城市模型的 **conceptual model and exchange format**。它关注城市对象的语义、几何表示以及对象之间的关系。

例如：

```text
Building
 ├── BuildingPart
 ├── WallSurface
 ├── RoofSurface
 ├── Door
 └── Window
```

这里表达的不只是：

> “这里有几个 triangles。”

而是：

> “这些 triangles 组成的是一面 WallSurface。”

所以 CityGML 回答的问题更接近：

```text
What is this object?
How is it semantically structured?
```

这也是为什么它特别适合 GIS、urban analysis 和 digital twin。

---

# 9. OSM：关于这个世界，我们知道什么？

然后是 OpenStreetMap。

OSM 很有意思，因为它甚至不需要保存完整的 3D geometry。

一个建筑可能只有：

```text
building=residential
height=30
building:levels=8
roof:shape=gabled
roof:height=5
```

但是这些简单的 tags 已经包含了大量 semantic information。

OSM 的 Simple 3D Buildings 本身就是基于 **2D footprints + additional tags + rule-based reconstruction** 的思路：实际的 3D reconstruction 由 renderer 或 server component 完成。

于是：

```text
OSM Data
    +
Renderer Rules
    ↓
3D Geometry
```

所以 OSM 更像是在回答：

```text
What do we know about this object?
```

它保存的是观察到的事实、属性和 tags。

---

# 10. CGA：这个世界应该怎样被构建？

而 CGA 问的是另外一个问题：

```text
How should this object be generated?
```

例如：

```text
Lot
 ↓
Extrude(height)
 ↓
Split floors
 ↓
Repeat(floor, 8)
 ↓
Split facade
 ↓
Repeat windows
 ↓
Create roof
```

这里保存的不只是 object。

保存的是：

> **生成 object 的 procedure。**

所以如果把它们放在一起：

```text
OSM
 ↓
What do we know?

CityGML
 ↓
What is it?

glTF / OBJ / FBX
 ↓
What does it look like?

CGA
 ↓
How should it be generated?
```

这几个东西并不是谁取代谁。

它们是在描述同一个数字世界的不同侧面。

---

# 11. 而 LLM 回答的是最后一个问题：人到底想要什么？

现在把 LLM 放进来，整个关系突然变得很清楚。

```text
Human
 ↓
Natural Language
 ↓
LLM
 ↓
What does the human want?
```

然后 LLM 可以连接下面不同层次的 representation：

```text
                 Human
                   ↓
            Natural Language
                   ↓
                  LLM
          "What do I want?"
                   ↓
          Semantic Interpretation
                   ↓
        ┌──────────┼──────────┐
        ↓          ↓          ↓
       OSM      CityGML      CGA
        │          │          │
 What we know   What it is  How to build
        │          │          │
        └──────────┼──────────┘
                   ↓
             Python / PyPRT
                   ↓
                  PRT
                   ↓
               Geometry
                   ↓
           glTF / 3D Tiles / ...
                   ↓
              GIS / WebGIS
```

这时候我觉得 LLM 在整个 3D pipeline 里的位置，就比单纯的：

```text
Prompt → 3D Model
```

清晰得多。

---

# 12. 从“生成模型”到“生成建模过程”

这也是我对这件事情最大的兴趣所在。

现在很多 Generative AI + 3D 的工作，关注的是：

```text
Prompt
 ↓
Geometry
```

也就是：

> **Generate the result.**

但 Procedural Modeling 给了另一条路线：

```text
Prompt
 ↓
Understanding
 ↓
Modeling Intent
 ↓
Modeling Operators
 ↓
Procedural Rules
 ↓
Geometry
```

也就是：

> **Generate the process.**

这两者的区别非常重要。

一个生成出来的 mesh 可以非常漂亮。

但它本身不一定告诉你：

```text
为什么有 8 层？
为什么这里有 balcony？
如果变成 12 层怎么办？
如果 roof 从 gabled 变成 flat 呢？
如果换一个 footprint 呢？
```

Procedural model 则天然保留了这种结构。

因为它保存的不是一次性的结果，而是：

> **一个可以重新执行、修改、组合和扩展的建模过程。**

---

# 13. 这对 GIS 尤其有意思

因为 GIS 天然就不是一个只关心“长得像不像”的领域。

GIS 里面本来就存在：

```text
Geometry
Attributes
Semantics
Topology
Coordinate Systems
Spatial Relationships
Rules
Constraints
```

例如 OSM 已经提供：

```text
Footprint
height
building:levels
roof:shape
building:part
...
```

CityGML 可以进一步提供 semantic city structure。

真实的 parcel、terrain、road network 又提供 geographic context。

所以一个非常自然的 pipeline 可以是：

```text
        Real World / GIS
               ↓
       OSM / CityGML / Data
               ↓
             Human
               ↓
        Natural Language
               ↓
              LLM
               ↓
       Modeling Intent
               ↓
     Parameters / CGA Rules
               ↓
        Python / PyPRT
               ↓
              PRT
               ↓
           Geometry
               ↓
       Cesium / WebGIS
```

这里 AI 不再是在一个空白世界里“想象”建筑。

它是在：

> **理解现实世界的数据和人的意图之后，对数字世界进行 procedural reconstruction 和 generation。**

这就比普通 text-to-3D 更接近 GIS 真正需要的东西。

---

# 14. 从乐高积木再回到“构建世界”

回到文章最开始那个乐高的比喻。

如果：

> **Geometry 是积木；**

那么：

> **Python 可以提供越来越丰富的积木和工具；**

> **CGA 是描述这些积木应该怎样组合的说明书；**

> **PRT 是真正按照说明书搭积木的机器；**

而：

> **LLM 是那个能够听懂人类语言，然后帮助我们理解、生成和修改说明书的 translator。**

于是整个系统变成：

```text
Human Imagination
       ↓
Natural Language
       ↓
      LLM
       ↓
Modeling Intent
       ↓
Procedural Description
       ↓
 Python + CGA
       ↓
   PyPRT / PRT
       ↓
    Geometry
       ↓
 Digital World
```

这时候，我们与计算机建模系统之间的关系开始发生变化。

以前，我们需要学习：

> **机器要求我们怎样描述世界。**

现在，我们开始尝试让机器理解：

> **人类想怎样构建世界。**

---

# 15. 也许真正有意思的不是 AI 生成 3D，而是“语言开始变成建模工具”

如果只是：

```text
Prompt → Mesh
```

我觉得它最终仍然只是另一种更方便的 content generation。

真正让我觉得有意思的是：

```text
Language
 ↓
Intent
 ↓
Semantics
 ↓
Rules
 ↓
Computation
 ↓
Geometry
 ↓
World
```

自然语言第一次有机会成为一种非常高层的 **modeling interface**。

我们不需要直接描述每一个 vertex。

甚至不需要直接告诉机器每一步具体应该调用哪个 operator。

我们只需要表达：

> **“我希望这个世界是什么样，以及它应该遵循什么规则。”**

剩下的过程，可以由 LLM、procedural rules、Python modules 和 deterministic runtime 一层一层翻译下去。

如果说得稍微浪漫一点：

过去，人类通过代码告诉计算机：

> **怎么画一个世界。**

而现在，我们开始尝试直接告诉计算机：

> **我们想要一个怎样的世界。**

然后让它自己找到构建这个世界的方法。

这也是为什么我现在觉得，**LLM + CGA + Python/PyPRT + GIS** 真正值得探索的方向，不是再做一个更强的 “3D Generator”。

而是做一个：

> **Procedural Modeling Copilot for the Digital World.**

或者更简单一点：

> **Geometry gives us the bricks.
> CGA gives us the instructions.
> Python gives us the toolbox.
> LLM lets humans describe the world they want to build.**

从数据描述世界，到规则构建世界，再到自然语言驱动这个过程。

这可能才是这条路线真正有意思的地方。
